# 3. 用最少文件建立清晰架构

需求是让新会话能找到“做什么、做到了哪里、依据是什么”。把这些答案分开管理，能避免状态埋进提示词，或把每次操作都复制进所有文件。本章结构是**推荐实践与本项目约定**，不是产品强制目录。

## 文件职责与必要性

| 对象 | 保存什么 | 是否必须 | 在本指南中的位置 |
| --- | --- | --- | --- |
| README | 目标、边界、快速开始和可点击索引 | 推荐最小入口；不是 ChatGPT 强制文件 | [README](../README.md) |
| AGENTS.md | Codex 稳定工作约定、范围、验证与报告 | 可选的受支持指令机制；本项目要求维护 | [AGENTS](../AGENTS.md) |
| Project Instructions | ChatGPT 项目内回答与工作约定 | 可选产品设置；不因仓库有同名文本而自动生效 | [可复制模板](../templates/chatgpt-project-instructions.md) |
| 资料与参考文件 | 原始输入、官方依据和访问范围 | 按任务需要，不上传所有内容 | [来源表](../references/SOURCES.md) |
| 当前状态 | 目标进度、当前阻塞、明确下一步 | 长期项目强烈推荐 | [STATUS](../management/STATUS.md) |
| 路线图/计划 | 未来优先级、完成条件、依赖 | 多阶段才需要；单次计划可留任务中 | [ROADMAP](../management/ROADMAP.md) |
| 任务日志 | 每次独立用户任务做了什么、证据与未完成项 | 本项目强制；不是 Codex 自动审计系统 | [TASK_LOG](../management/TASK_LOG.md) |
| 变更记录 | 对读者有意义的内容/结构变化 | 可选；不替代 Git 提交 | [CHANGELOG](../management/CHANGELOG.md) |
| 决策记录 | 重要选择、理由、替代方案、失效条件 | 有长期决定时才写 | [DECISIONS](../management/DECISIONS.md) |
| 提示词/模板 | 可复制任务入口 / 文件内容骨架 | 重复需求才抽取 | [提示词](../prompts/04-execute-task.md)、[模板](../templates/status.md) |
| 目录索引 | 文件发现与跨主题导航 | 本项目由 README 承担，不再维护第二份总目录 | [完整索引](../README.md#完整文件索引) |
| 案例与验证 | 操作如何落实、哪些实际观察过 | 区分教学演练与实际记录 | [本库案例](../examples/04-this-guide.md)、[验证](../management/VALIDATION.md) |

## 最小项目与扩展项目

很小的个人项目可只有 README 和一个状态区；任务在其中短记即可。资料明显增加后再分 docs/ 和 references/；确实发生跨日恢复或并行才强化状态与日志。迁移模板时保留它解决的问题，不要机械复制本库全部管理文件。

本项目之所以拆出五类管理文件，是因为用户明确要求长期演进和逐任务记录。它们各写一份事实：任务经过在日志；当前结论在状态；长远候选在路线图；不可轻易改变的选择在决策；读者值得注意的版本变化在变更记录。其余地方链接该记录。

## ChatGPT 与仓库怎样配合

1. 在仓库先形成经过审查的正式文件。
2. 将必要摘要和日期/提交版本带入 ChatGPT Project，手动粘贴项目指令，上传或通过有权限的工具访问所需材料。
3. 结束讨论时，区分“候选结论”与“已确认决定”，交给 Codex 检查并更新对应文件。
4. 文件更新后检查旧上传副本是否过期，明确刷新时间；不能假定上传文件会随 Git 自动同步（O1、O2）。

不需要把全部日志上传成项目资料。先提供 README、STATUS 和当前主题的少量材料；需要追溯时再读取相应任务或提交。按需读取的方法见 [上下文管理](04-context-memory-files.md)。
