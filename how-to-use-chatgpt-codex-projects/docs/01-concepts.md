# 1. 先分清产品与持久化对象

当用户说“我的项目”，可能指聊天资料集合，也可能指磁盘目录、Git 仓库或任务看板。先回答“内容在哪里、谁能访问、怎样保存、用哪个工具执行”，才能判断功能是否满足需要。本章产品事实核验于 **2026-11-01**；来源统一登记在 [SOURCES](../references/SOURCES.md)。

## Codex 项目、目录、仓库与工作树

- **工作目录（working directory）**：命令当前执行的位置，决定相对路径的含义；进入目录本身不会创建仓库。
- **仓库（repository）**：Git 管理的对象与历史。一个仓库可容纳多个独立文档项目；本指南就是 `ChatGPT_CodeX` 的一个子目录。
- **工作树（working tree）**：当前检出的文件。`git status` 比较工作树、暂存区和提交；文件保存在磁盘还不代表已提交。
- **Git worktree**：同一仓库附加的检出目录，共享 Git 对象和引用、拥有各自工作文件。适合本地并行分支，不是新的独立仓库；通常不能同时检出同一分支到两个 worktree（O10）。
- **Codex Cloud 环境与任务**：当前文档描述为先准备和发布可复用环境，再从环境发起任务，每个任务有自己的工作区（O6）。正在运行的进程与未推送提交不能据此被理解为跨任务自动持续同步。不要在已隔离云任务中机械增建 worktree。

## 五种上下文材料各有职责

目录提供空间归属；聊天保存探索过程；上下文是本次模型可利用的信息；记忆帮助挑选与延续相关信息；工作指令规定行为。它们不是同一份数据的五个名称。项目指令也不会自动把 README 的每个字加载为上下文。

长期项目不能只靠聊天：聊天可能很长，记忆会选择相关内容，产品保留政策和权限可能变化，结论也可能被后来纠正。把正式结论、状态和决定写入文件，是一种**推荐管理机制**，不是修复一个平台承诺“永远记住全部细节”的功能。

例如，在 ChatGPT 中讨论“先做中文首版”，随后让 Codex 建英文网站，并不表示两个工具达成了同一决策。先把已确认范围写入 STATUS/DECISIONS，再让 Codex读取，才能建立可核查交接。下一步见 [选型与边界](02-project-decisions.md) 和 [上下文](04-context-memory-files.md)。
