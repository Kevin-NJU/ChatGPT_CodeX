# 2. 什么时候创建、拆分或合并项目

项目的价值来自复用背景、统一边界和保留成果。只有一次答案的任务，管理文件可能比任务本身还贵。本章是**推荐实践**；产品能力边界见 [概念表](01-concepts.md)。

## 从任务产物做决策

| 要回答的问题 | 若是 | 建议起点 |
| --- | --- | --- |
| 是否只需一次解释，后面无需复用资料或成果？ | 如解释一个 Git 命令 | 普通对话，必要时把结论保存到已有手册 |
| 是否反复围绕同一目标讨论并复用资料？ | 如一学期课程、长期写作 | ChatGPT Project；用简短状态摘要保留关键进展 |
| 是否要修改本地文件、运行命令、测试或审查差异？ | 如维护 Python 工程、批量整理文档 | Codex + 现有目录；需要历史追溯时用 Git |
| 是否既要讨论研究又要维护可审查成果？ | 如本指南 | ChatGPT 做分析，Codex 维护仓库，显式交接 |
| 是否需要跨任务/跨人排期与责任可视化？ | 多个 Issues/PR、多个负责人 | 视规模引入 GitHub Projects；个人小库先用 ROADMAP |

执行流程：先确定可验收产物 → 判断背景是否反复复用 → 判断是否需要文件执行/版本追踪 → 选择最少工具 → 明确信息的正式存放位置 → 做一次小任务，观察维护负担。普通对话也能完成复杂分析，不能以“字数多”作为创建项目的唯一理由。

## 边界由目标、资料、权限与生命周期共同决定

创建前写出一句目标、允许输入、预期产物、非目标和完成/暂停条件。例如“维护 AI 项目使用方法，面向个人长期项目，不开发网站”。主题名称相近也可能需要拆开：个人日记和团队工作报告的权限不同；一篇公开综述和含受限受试者数据的研究底稿不可因都叫“科研”而直接合并。

| 观察到的信号 | 采取行动 | 验收方式 |
| --- | --- | --- |
| 同一组指令不断出现互相冲突的例外 | 按独立目标/权限拆分，先写迁移映射 | 每个子项目能写出独立目标且不依赖复制大段状态 |
| 每次都读大量无关资料才能定位下一步 | 先改善入口和按需索引，仍无效才拆分 | 一次典型任务只需入口和相关章节 |
| 两个项目持续复制相同决策和资料 | 选一个正式来源，另一个链接；生命周期也一致再合并 | 以后修改只在一处发生 |
| 项目很小却已有多个长期闲置管理文件 | 合并管理信息到状态页 | 仍能找到下一步、关键决定与验证记录 |
| 仅共享一个方法但目标不同 | 提取公共方法或交叉引用 | 不为了共享一个模板而合并权限边界 |

拆分顺序：先确认需保留历史和访问边界 → 建立旧路径到新路径映射 → 移动并修复链接 → 更新入口、状态、日志 → 在独立分支审查。合并也要先决定哪个版本是正式事实，不能将互相矛盾的决定简单拼接。

## 三个判断示例

1. **论文阅读**：一篇概念答疑用普通对话即可；整个学期需要反复定位论文、假设与实验结果，适合 ChatGPT Project，加仓库保存研究笔记。未获版权许可的全文不直接公开入库。
2. **代码修复**：只解释报错可用 Chat；若必须复现、改文件和跑测试，用 Codex + 仓库。产品聊天容器不能代替测试环境。
3. **本知识库**：主题是项目管理，与已有“AI 辅助阅读手册”的目标不同，所以在同一仓库建独立目录，不复制对方全部理论，不新建仓库、网站或看板。

如果无法用一两句话说明分开的价值，先在现有项目加一个章节。规模扩大后再根据真实摩擦调整，而不是提前为所有未知主题造空目录。实例展开见 [学习](../examples/01-research.md)、[代码](../examples/02-code-project.md)、[知识库](../examples/03-knowledge-base.md)。
