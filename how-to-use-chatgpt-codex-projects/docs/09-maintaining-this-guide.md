# 9. 如何维护本知识库本身

本章是本库的操作手册。长期维护的对象包括内容正确性、资料新鲜度和恢复入口，不以文件数量为成功标准。规则来自用户要求，机制落实在 [AGENTS](../AGENTS.md)。

## 新问题先找归属

1. 用 `rg` 搜索同义词和相关概念；README 定位已有章节。
2. 属于已存在的问题，就更新原章；独立问题有足够实质内容时才新建文档。
3. 多章共享的方法写一处，其他位置用链接；冲突先查版本、套餐和定义差异。
4. 新文件加入 README 完整索引；移动文件修复所有入链。规划留 ROADMAP，不创建假装完成的空章节。

例：“项目记忆是否能在创建后切换”应更新上下文章和 O1 来源记录，不再新建一个“记忆新功能完整指南”。旧结论的历史背景写到有意义的 CHANGELOG 或关联任务，不让读者在正文中面对两套未标日期的相反指令。

## 一次任务怎样落盘

| 判断 | 更新位置 | 避免做什么 |
| --- | --- | --- |
| 每次独立任务的实际操作与证据 | TASK_LOG 追加一条 | 不逐条终端命令建日志，不预写成功 |
| 当前进度或下一步改变 | STATUS | 不复制完整任务经过 |
| 对读者有意义的内容或结构变化 | CHANGELOG | 不记录每个错字或每次命令 |
| 形成影响未来的长期选择 | DECISIONS | 不把普通执行步骤包装成决策 |
| 值得以后研究但尚未完成 | ROADMAP | 不在 STATUS 写成已交付 |
| 新来源或旧功能的核验范围改变 | SOURCES | 不因 HTTP 200 就声称做过界面实测 |

调查没有改正文仍写任务记录；用户明确要求全只读时服从，回复给待追加日志。任务日志是事实证据入口，不是模型每一步的私有推理记录。

## 资料复核与过期处理

默认建议每季度复核一次易变产品功能，产品公告/界面明显变化时提前复核；这是本库建议，**未配置自动定时任务**。优先复查 memory 模式、Work/Codex 入口、GPTs 迁移、权限与计费。稳定的文件管理建议可较低频复查。

复核步骤：访问官方正文并记实际日期 → 提取版本/套餐/平台条件 → 与当前章逐项比较 → 需要时在无秘密测试项目实测 → 更新正文和 SOURCES → 旧资料标注“被替代”并链接新依据。官方页面不可访问时写访问失败与现有证据范围，不据此猜测功能已删除。新说法若与实际账号不符，记录二者，暂不声称已解决。

维护者可用 [定期检查](../prompts/06-periodic-review.md) 和 [扩展提示词](../prompts/05-expand-knowledge-base.md)。AGENTS 保持边界与触发规则；新专题细节应留在 docs/，不要无限增加长期指令。

## 检查方法与证据

在仓库根目录先运行：

```bash
git status --short --branch
git diff --check -- how-to-use-chatgpt-codex-projects/
```

上述 diff 不覆盖未跟踪文件；新增文件还要逐个审查正文与空白，或在授权暂存后用 `git diff --cached --check`。检查所有 Markdown 相对路径目标及标题/显式锚点、围栏闭合、README 对全部文件可达，并人工检查产品边界、来源与重复信息。首版使用 Python 标准库进行一次性结构检查；证据和局限见 [VALIDATION](../management/VALIDATION.md)。尚未引入网站、依赖包或常驻服务。

只有结构错误反复出现且人工检查成本明显增长，再考虑在项目内保留小型检查脚本，并用已知坏链接/坏锚点样本验证它确实能失败。无需为了纯文档建立复杂 CI。外链 HTTP 成功不证明正文论断正确；文档通过检查也不证明产品所有界面行为已实测。

## 日志增长、归档与交接

日志大到明显影响检索时，先提炼当前状态，再按年份将旧条目移入带索引的归档文件；保留原任务 ID 和入链，不丢弃重要失败证据。达到这个实际需要前不预建空归档目录。

交接必须提供实际仓库、路径、分支/提交、未提交差异、已验证和未验证项、下一步；使用 [迁移提示词](../prompts/08-handoff.md)。新会话先核对文件，不把交接摘要视作不可质疑事实。恢复无需重新搭建整个结构，也不将其他项目的约定套入本库。
