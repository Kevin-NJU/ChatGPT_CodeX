# 案例 3：持续扩展的个人知识库

**性质：教学演练。** 假定用户持续收集“个人知识管理”方法，材料包含笔记、官方说明与亲身经验，希望避免每次问同一个问题。

## 是否创建项目与结构

这是反复使用资料、持续修订结论的任务，适合 ChatGPT Project 讨论与 Git 仓库存放正式知识结合。若只收藏三个链接，先用单个 README 即可；随着实际内容增长再拆 docs/、references/、prompts/、management/，不预建无内容分类。

正式来源规则：理论与方法放章节，输入登记放 references，日常事实放任务日志，当前进度放 STATUS。聊天是探索工作区，不是所有结论的唯一档案。

## 初始化指令

```text
请在 [知识库目录] 建立“个人知识管理实践库”，主要解决 [具体问题]。
先搜索已有同主题内容和适用规范，设计最小入口及状态，然后写一章可直接使用的方法与一个明确标识的教学例子。
区分文献事实、作者建议和我的经验，给来源与日期；保存材料前确认公开范围。
只改 [允许路径]；新增主题先判断能否整合原章，目录索引可点击。
按独立任务记录事实，实质变化写 CHANGELOG，重要长期决定写 DECISIONS，未完成研究进 ROADMAP。
本次仅本地生成和检查，不推送；结束给出差异、证据和下一步。
```

## 日常使用

用户新增材料“上下文压缩会遗失什么？”时先查已有“上下文管理”章节，定位新增证据，再补到相应段落；不是为每份材料开一篇类似标题的文章。把官方机制与使用经验分别标记，来源改变时追溯所有依赖该来源的页面。

典型产物是一个已有章节的更新、来源登记和一条任务日志，而非十个新的管理文件。模板只有复用需求出现才抽取；提示词不复制正文全部理论。

## 跨日继续与维护

下一会话从 STATUS 看到“待核验项目记忆边界”，查相关决定与来源记录后工作。若上一会话只是提出候选结论，未经查证不能写成用户已确认决定；若仅在 ChatGPT 上传了旧版本，需显式刷新，而不是假定跟随 Git。

日志保留每次任务事实，CHANGELOG 仅记读者有必要知道的结构或结论变化。定期查坏链接、重复、矛盾和失效功能；无法核验则保留边界与候选研究。日志膨胀后再按年份归档，保留入口和历史 ID。可迁移验收：新协作者从入口能找到当前状态、正式来源、最近决定和下一件工作。

本仓库实际建立的项目则见 [本指南案例](04-this-guide.md)，不要把本教学设计的能力写成已实测。
