# 案例 2：Codex 持续维护 Python 工程

**性质：教学演练，未创建或运行真实代码服务。** 假定已有 Python 项目，用户要求修复 CSV 导入时空字段导致的错误，并保留既有行为。

## 需求与工具选择

需要读取代码、复现、改文件和跑测试，选择 Codex + Git。ChatGPT 可先讨论需求，但讨论不替代环境中的复现。README、依赖清单/锁文件、tests/、适用 AGENTS 和简短状态是优先材料；不为这次修复另建嵌套仓库。

建议沿用工程现有 src/、tests/、文档和包管理器；若缺长期进度文件，再按规模加入 management/STATUS.md 与任务记录。不要因本指南列出五类管理文件，就重构一个已经稳定工作的工程。

## 初始化与任务指令

```text
请接手 [实际代码目录]，修复 [CSV 空字段的可复现输入与预期行为]。
先确认仓库、适用 AGENTS、工作区、README、Python 版本和依赖锁文件；用既有安装及测试方式，不改无关依赖。
允许修改 [导入模块与相关测试路径] 及 [状态/日志路径]；不改部署配置，不访问生产数据。
先复现，再做最小修正，运行相关既有测试和必要回归；报告实际命令、测试数与失败/跳过项。
验收：空字段按明确规则处理，正常 CSV 行为不回归，日志和状态有证据。
允许创建工作分支、提交和推送该分支及 PR，不合并、不部署、不强推。
```

先从清单推断正确工具，而非把 `pip install -r requirements.txt` 或 `pytest` 当所有 Python 项目的统一命令。锁定安装、工具激活和系统依赖都要在该项目环境实际验证。

## 日常执行

创建能失败的复现或使用既有失败用例 → 观察错误 → 修复导入路径 → 相关测试验证 → 检查无关差异 → 记录结果并提交具体路径。环境网络失败与产品代码缺陷分开诊断；不能因为没装好测试运行器就把失败归为代码 bug。

如果包签名、下载校验或 TLS 失败，先修复信任与来源，不关闭验证。如果需要数据库，用隔离开发服务，不在生产库“测试”。单有进程或开放端口不够，需代表性请求验证行为。

## 跨日继续

STATUS 指出修复在何分支、最后通过什么检查、是否还有回归未跑。新会话先核对实际 HEAD 和未提交差异，再根据现有脚本恢复环境；云端新任务不假定接收旧任务所有未提交改动。终端进程需要重启，环境准备的文件与服务启动步骤应分开。

## 日志、并行与失败恢复

一次修复任务一条日志：输入、实际复现、改哪些模块/测试、通过/失败/跳过数量、提交与推送状态。任务量增大后用 PR/Issues 管理排期，多个协作者再考虑 GitHub Projects。

并行可让一人维护导入器、一人修文档，但共享状态和任务日志由最终整合者处理；独立分支合并时验证兼容性。冲突先理解双方意图，不覆盖别人的修复；回滚优先可审查的反向变更。该流程的实际成功与否需要在真实工程执行，本案例不提供虚构测试数或 PR 地址。
